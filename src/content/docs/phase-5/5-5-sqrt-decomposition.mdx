## 1. Why this topic exists

Here is a small problem. An array has $n = 10^5$ numbers and there are $q = 10^5$ operations. An operation either sets one number $a_k$ to a new value $x$, or asks how many of the numbers in $a_l, \dots, a_r$ are smaller than $x$.

Counting inside each range costs up to $n \cdot q = 10^{10}$ steps, about 100 seconds. A Fenwick tree ([topic 5.2](../5-2-fenwick/)) counts sums, but "smaller than $x$" depends on the values, and one tree over positions cannot answer it. A segment tree ([topic 5.3](../5-3-segment-tree/)) needs a node that combines the answers of its halves, and a node of one number cannot say how many of its values are below $x$.

The key idea: cut the array into blocks of about $\sqrt n$ consecutive positions and keep, for each block, a summary that answers the question for the whole block in one step. Here the summary is the block's values in sorted order, so one binary search counts the values below $x$. A range is then at most two ragged ends of fewer than $\sqrt n$ positions, handled one by one, and at most $\sqrt n$ whole blocks, about $\sqrt n \log n$ steps in all, and a change repairs one block. This is **square-root decomposition**.

Two more ideas of the same size appear in this topic. A **threshold** of about $\sqrt n$ splits the cases: if a parameter is large, few steps or few items are involved; if it is small, all small cases can be precomputed together. And a **rebuild every $\sqrt q$ changes** keeps a table that is slow to rebuild: the table is rebuilt once per batch of changes, and a question looks at the few changes since then one by one.

### What this topic does not cover

## 3. Definitions

- A **block decomposition** of an array of $n$ positions with **block size** $B$ cuts the positions into blocks of $B$ consecutive positions (the last block may be shorter): block $b$ holds positions $bB, \dots, \min(n, (b+1)B) - 1$. Example: $n = 10$, $B = 3$ gives the blocks $0..2$, $3..5$, $6..8$ and $9..9$. There are $\lceil n / B \rceil$ blocks.
- A range $[l, r]$ is split into **partial blocks** (the first and the last block, if the range does not cover them completely) and **whole blocks** between them. Example: with $B = 3$ the range $[2, 8]$ has the partial position 2 and the whole blocks 1 and 2.
- A **threshold** $B$ splits a quantity into the **large** ones ($\ge B$) and the **small** ones ($< B$). Example: for steps $k$ of a progression, the large steps are those with $k \ge B$.
- The **step sum** with start $p$ and step $k$ is $a_p + a_{p+k} + a_{p+2k} + \dots$, up to the end of the array.
- A **rebuild batch** is a group of $B$ changes after which a table is rebuilt from scratch. Example: with $B = 2$ and marks arriving one at a time, the table is rebuilt after the second, fourth, sixth mark; a question after the fifth mark sees the table of the fourth and one recent mark.

## 4. Theory and proofs

### 4.1 Blocks with a note for the whole block

**Theorem 5.5.1 (blocks, range add and range sum).** Cut the array into blocks of size $B$. Keep for each block $b$ the true sum $\text{sum}[b]$ and a number $\text{add}[b]$, and for each position a number $a[i]$, so that the true value of position $i$ is $a[i] + \text{add}[b(i)]$. To add $x$ to a range: for each partial position do $a[i] \mathrel{+}= x$, $\text{sum}[b(i)] \mathrel{+}= x$; for each whole block do $\text{add}[b] \mathrel{+}= x$, $\text{sum}[b] \mathrel{+}= x \cdot \text{len}(b)$. To sum a range: add $a[i] + \text{add}[b(i)]$ for each partial position and $\text{sum}[b]$ for each whole block. Each operation takes at most $2(B - 1) + \lceil n / B \rceil$ steps, which is $O(\sqrt n)$ for $B \approx \sqrt n$.

:::tip[In plain words]
Treat a whole block as one thing: a note "everyone here got $x$" and the total of the block. For the ragged ends of a range, which cut a block in the middle, change or read the positions one by one. There are at most two ragged ends of less than $B$ positions each, and at most $n / B$ blocks in between; with $B = \sqrt n$ both are about $\sqrt n$.
:::

**A tiny instance.** $a = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3]$, $B = 3$: the block sums are $8, 15, 13, 3$. Add 10 to $[2, 8]$: position 2 is a partial position ($a_2$ becomes 14, $\text{sum}[0] = 18$); blocks 1 and 2 are whole and get the note 10 each, with the sums $15 + 30 = 45$ and $13 + 30 = 43$. The sum of $[1, 9]$ is $1 + 14$ (partial positions of block 0) $+ 45 + 43 + 3 = 106$.

**Proof.**
1. *Invariant:* the true value of position $i$ is $a[i] + \text{add}[b(i)]$, and $\text{sum}[b]$ is the sum of the true values in block $b$. It holds at the start (all notes 0).
2. Adding $x$ to a partial position raises its true value by $x$ and the true sum of its block by $x$: the invariant holds.
3. Adding $x$ to a whole block raises every true value of the block by $x$, because $\text{add}[b]$ is part of each of them, and the true sum by $x \cdot \text{len}(b)$: the invariant holds.
4. A sum reads the true values of partial positions and the true sums of whole blocks, which is exactly the sum of the true values of the range (each position once).
5. A range has partial positions only in its first and last block, fewer than $B$ in each, and at most $\lceil n / B \rceil$ whole blocks, each costing one step. $\square$

:::note[This proof needs]
1. A change to the whole block must be summarised by a note that can be applied to the stored block sum in one step (here $x \cdot \text{len}$); the note is added to the true value of every position and never needs to be pushed down.
2. The last block can be shorter than $B$; its length is used in the formulas.
3. The sums need 64 bits.
:::

<TheoremCode unit="5.5/thm-1" />

The first example prints the block sums 8, 15, 13, 3; after the addition the notes are 0, 10, 10, 0 and the sums are 106, 45 and 3. The check compares with a plain array on random operations, for every $n$ up to 30 and the block sizes 1, 2, 3, 5 and 7.

### 4.2 Blocks that keep a sorted copy

**Theorem 5.5.2 (blocks, count of smaller values with changes).** Keep a sorted copy of the values of each block. The number of positions in $[l, r]$ with a value smaller than $x$ is found by looking at each partial position and by a binary search in the sorted copy of each whole block. A change of one value is done by removing the old value from the sorted copy of its block and inserting the new one. A query takes $O(B + (n / B) \log B)$ steps and a change $O(B)$.

:::tip[In plain words]
A block cannot say how many of its values are below $x$ unless it keeps its values in order. Keep them in order, so that one binary search per whole block counts them. A change touches one block, and putting one value in a sorted list of $B$ values costs about $B$ moves.
:::

**A tiny instance.** $a = [5, 2, 8, 1, 9, 3, 7, 4, 6]$, $B = 3$: the sorted copies are $[2, 5, 8]$, $[1, 3, 9]$, $[4, 6, 7]$. Count the values below 5 in $[1, 7]$: positions 1 and 2 (values 2 and 8) are partial and only the 2 counts; the whole block 1 has $\text{lower\_bound}(5)$ at index 2 in $[1, 3, 9]$, so 2 values; positions 6 and 7 (values 7 and 4) are partial and only the 4 counts. Total $1 + 2 + 1 = 4$. After $a_4 = 0$ the copy of block 1 is $[0, 1, 3]$ and the same query gives 5.

**Proof.**
1. *Invariant:* for every block, the sorted copy holds exactly the values of the block, in non-decreasing order.
2. For a whole block, the number of its values below $x$ is the index returned by a binary search for the first value $\ge x$ in the copy. A partial position is counted by comparing its value.
3. A change from $y$ to $z$ at position $i$: remove one copy of $y$ from the sorted copy of its block (found by binary search, then shifting the later elements), insert $z$ at its place (the same), and set $a[i] = z$. The copy again holds the values of the block, in order (step 1).
4. The query makes fewer than $2B$ comparisons for partial positions and at most $\lceil n / B \rceil$ binary searches of $O(\log B)$ steps each. The change moves at most $B$ elements twice. $\square$

:::note[This proof needs]
1. The question can be answered for a whole block from a sorted copy. Counts below or above a bound, and the $k$-th smallest by binary search over the answer, fit; a question that needs the elements in their original order does not.
2. With $B = \sqrt{n \log n}$ a query costs about $\sqrt{n \log n}$ and a change the same.
3. Equal values are allowed; the removal erases exactly one of them.
:::

<TheoremCode unit="5.5/thm-2" />

The first example prints the sorted copies, the count 4 and the counts after the change (5 and 3). The check compares with a loop on random sets and queries, for every $n$ up to 30 and five block sizes.

### 4.3 Small steps from a table, large steps by walking

**Theorem 5.5.3 (threshold on the step).** Let $B$ be a threshold. For every step $k < B$ keep the table $T_k[p] = a_p + T_k[p + k]$ (with $T_k[p] = 0$ for $p \ge n$). Then the step sum with start $p$ and step $k$ is $T_k[p]$ if $k < B$, and otherwise is found by walking $p, p + k, p + 2k, \dots$ in at most $\lceil n / B \rceil$ steps. The tables take $O(nB)$ time and memory, so $q$ questions take $O(nB + q n / B)$ time, which is $O((n + q)\sqrt n)$ for $B \approx \sqrt n$ and $q$ about $n$.

:::tip[In plain words]
A big step leaves the array after only a few jumps, so just make the jumps. A small step has only a few different values (fewer than $B$), so for each small step precompute the answer from every start. The two costs are balanced at $B \approx \sqrt n$.
:::

**A tiny instance.** $a = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3]$, $B = 3$. For $k = 2$ the table is $T_2 = [19, 20, 16, 19, 12, 18, 7, 9, 5, 3]$ (for example $T_2[7] = 6 + T_2[9] = 6 + 3 = 9$). The question $(p = 1, k = 2)$ is $T_2[1] = 20 = 1 + 1 + 9 + 6 + 3$. The question $(p = 4, k = 7)$ has $k \ge B$: walk $4, 11$; the sum is $a_4 = 5$.

**Proof.**
1. The step sum with start $p$ and step $k$ is $a_p$ plus the step sum with start $p + k$ and the same step, and it is 0 when $p \ge n$. So $T_k[p] = a_p + T_k[p + k]$ is the step sum, by induction from the right end.
2. Filling $T_k$ from $p = n - 1$ down to 0 takes $n$ steps, and there are $B - 1$ tables.
3. For $k \ge B$ the walk visits $p, p + k, \dots$ below $n$, at most $\lceil n / k \rceil \le \lceil n / B \rceil$ positions.
4. A question costs 1 step for $k < B$ and at most $\lceil n / B \rceil$ steps otherwise. The total is $O(nB + q \lceil n / B \rceil)$; the two terms are equal for $B = \sqrt q$, which gives $O(n \sqrt q + q)$, and $O((n + q)\sqrt n)$ when $q$ is about $n$. $\square$

:::note[This proof needs]
1. The question depends on the step only through a table that can be built from the right end; a question where the table of a small step needs more than $O(n)$ steps does not fit.
2. Memory is $n B$ numbers, which limits $B$ (for $n = 10^5$ and $B = 300$ it is $3 \cdot 10^7$ numbers).
3. A shorter table size $n + k$ avoids a test for $p + k \ge n$.
:::

<TheoremCode unit="5.5/thm-3" />

The example prints the table for $k = 2$ and the answers for four questions. The check compares with a loop for every start and every step up to $n + 2$ on random arrays, for several thresholds.

### 4.4 Few large values

**Theorem 5.5.4 (few values can be large).** For an array of $n$ positive integers let $H$ be the set of values $x$ that occur at least $x$ times in the whole array. Then $|H| \le \sqrt{2n}$. A value $x \notin H$ occurs fewer than $x$ times in the array, hence in every range. So the number of values that occur *exactly* $x$ times in $[l, r]$ is the number of $x \in H$ whose count in $[l, r]$ is exactly $x$, and all $q$ questions are answered in $O(\sqrt{n} (n + q))$ steps: for each $x \in H$ one pass builds the prefix counts, and each question looks at two of them.

:::tip[In plain words]
A value $x$ can only occur exactly $x$ times in a range if it occurs at least $x$ times in the whole array. The total number of places is $n$, and different values of $H$ use at least $1 + 2 + 3 + \dots$ of them. So there are only about $\sqrt{2n}$ candidates, and for each candidate one pass over the array and the questions is enough.
:::

**A tiny instance.** $a = [3, 1, 2, 2, 3, 3, 1, 3]$: the counts are $c_1 = 2$, $c_2 = 2$, $c_3 = 4$. So $H = \{1, 2, 3\}$ (each has at least its own value as a count). The question $[0, 4]$ holds $3, 1, 2, 2, 3$: the value 1 occurs once (yes), 2 occurs twice (yes), 3 occurs twice (no), so the answer is 2.

**Proof.**
1. Every $x \in H$ takes at least $x$ of the $n$ positions, and different values take different positions, so $\sum_{x \in H} x \le n$.
2. The values of $H$ are different positive integers, so $\sum_{x \in H} x \ge 1 + 2 + \dots + |H| = |H|(|H| + 1)/2$. Hence $|H|(|H|+1)/2 \le n$ and $|H| \le \sqrt{2n}$.
3. If $x \notin H$, then $x$ occurs fewer than $x$ times in the whole array and fewer than $x$ times in any range; it can never be counted.
4. For $x \in H$ the prefix counts $P_x[i]$ give the number of occurrences in $[l, r]$ as $P_x[r + 1] - P_x[l]$. One pass builds $P_x$ in $O(n)$ steps; checking all $q$ questions takes $O(q)$ steps.
5. The total is $|H| \cdot O(n + q) = O(\sqrt{n}(n + q))$. $\square$

:::note[This proof needs]
1. The answer depends on a value only through its count in the range and its own size. A condition like "the count is at least $t$" for a fixed $t$ gives the same kind of bound (at most $n / t$ values qualify).
2. The values should be positive integers (or mapped to them); values above $n$ are skipped.
3. The tables for all candidates at once would take $O(n \sqrt n)$ memory; processing one candidate at a time takes $O(n + q)$.
:::

<TheoremCode unit="5.5/thm-4" />

The first example is the tiny instance with four questions (1, 2, 1, 1). The second builds an array of length 5050 in which every value $1..100$ occurs as often as its own size: all 100 values qualify, and 100 is exactly the bound $\sqrt{2n}$. The check compares with a count inside each range on three thousand random arrays and sets of questions.

### 4.5 Rebuilding after every few changes

**Theorem 5.5.5 (rebuild every $B$ changes).** Marks are added one at a time to a tree of $n$ vertices. A structure keeps a table $T$, where $T[v]$ is the distance from $v$ to the nearest vertex marked before the last rebuild, and the list $P$ of the marks made since. A mark adds the vertex to $P$, and when $|P| = B$ a rebuild runs a search that starts from every marked vertex at once, fills $T$ in $O(n)$ steps and empties $P$. The answer for a vertex $v$ is $\min(T[v], \min_{m \in P} \text{dist}(v, m))$. Then the answer is the distance from $v$ to the nearest marked vertex, and $k$ marks and $q$ questions cost at most $\lfloor k / B \rfloor \cdot O(n) + q \cdot (B - 1) \cdot c$ steps, where $c$ is the cost of one tree distance. With $c = O(1)$ and $B \approx \sqrt n$ this is $O((k + q) \sqrt n)$.

:::tip[In plain words]
Do the slow full rebuild only after every $B$ changes. Between two rebuilds the table is a little out of date, but only by the at most $B - 1$ recent changes, and a question can look at those one by one. If a rebuild costs $n$ and one recent change costs 1 per question, the two costs balance at $B \approx \sqrt{n}$ when the numbers of changes and of questions are about $n$.
:::

**A tiny instance.** The path $0 - 1 - 2 - 3 - 4 - 5 - 6$ and $B = 2$. Mark 0: $P = [0]$, no rebuild yet; the answer for vertex 3 is $\text{dist}(3, 0) = 3$. Mark 6: $|P| = 2 = B$, so the search from $\{0, 6\}$ gives $T = [0, 1, 2, 3, 2, 1, 0]$ and $P = []$. The answer for vertex 5 is $T[5] = 1$. Mark 3: $P = [3]$; the answer for vertex 2 is $\min(T[2], \text{dist}(2, 3)) = \min(2, 1) = 1$.

**Proof.**
1. *Invariant:* after every operation, $T[v]$ is the distance to the nearest vertex of the marks made before the last rebuild, and $P$ lists exactly the marks since. It holds at the start (no marks, $T = \infty$, $P$ empty).
2. A mark only appends to $P$; if $|P| = B$ the rebuild recomputes $T$ for all marks made so far (a search from all of them at once gives, for each vertex, the distance to the nearest one) and empties $P$. The invariant holds after the rebuild.
3. The set of all marks is the marks before the last rebuild together with $P$. The distance to the nearest vertex of a union is the smaller of the distances to the nearest vertex of each part, so $\min(T[v], \min_{m \in P} \text{dist}(v, m))$ is the true answer.
4. A rebuild happens after every $B$-th mark, so there are at most $\lfloor k / B \rfloor$ of them, each $O(n)$ steps.
5. A question looks at the fewer than $B$ vertices of $P$, at cost $c$ each. Adding up gives the bound. $\square$

:::note[This proof needs]
1. Marks are only added, never taken away: the table cannot forget a vertex that was marked before the last rebuild.
2. The answer for the union is the smaller of the answers for the parts (a minimum, or a sum or count of independent parts); a question that is not of this kind cannot combine the table with a recent mark.
3. A rebuild costs about $O(n)$ and a recent mark one step per question, so that $B \approx \sqrt n$ balances them.
:::

## 6. Templates

Four templates. Each shows only the structure or function that matters; the program around it reads the input. Each is checked against a brute force that follows the statement directly (scan the range, search from the vertex), on thousands of random small inputs and on fixed tests with a single element, equal values and the largest numbers.

### Set a range to one value, sum of a range (Theorem 5.5.1)

<CodeSnippet unit="5.5/block-assign-sum" />

**How it works.** The array is cut into blocks of $B \approx \sqrt n$ positions. A block that lies fully inside the range is not touched position by position: it gets the flag `asg[b]` and the value `val[b]`, and its sum becomes `x * length`. A block that the range only cuts through is first brought up to date by `push` (it writes the pending value into `a[]` and clears the flag), and then the positions inside the range are changed one at a time while `sum[b]` is repaired by `x - a[i]`. A query takes the sum of the whole blocks and reads the single positions of the others after `push`. The length of the last block may be smaller than $B$, so the formulas use `hi(b) - lo(b) + 1`.

**Alternative formulation.** A segment tree with an assignment tag (topic 5.3, Theorem 5.3.4) does this in $O(\log n)$ steps per operation and is the better choice when it fits. Blocks are the choice when the summary of a block cannot be composed as a tag, or when a block is rebuilt from its positions anyway.

### Count the values between two bounds, with changes (Theorem 5.5.2)

<CodeSnippet unit="5.5/block-count-between" />

**How it works.** Each block keeps its values in a sorted copy. `countBetween` reads the first and last blocks position by position and uses two binary searches in each whole block: `upper_bound(hi) - lower_bound(lo)` is the number of values from `lo` to `hi`. `set` removes one copy of the old value from the sorted copy of its block (`erase(lower_bound(...))`) and inserts the new value in its place (`insert(upper_bound(...))`), $O(B)$ moves, then writes `a[i]`. The program uses $B = \lfloor \sqrt n \rfloor$.

**Alternative formulation.** Offline, a Fenwick tree with sorted questions (topic 5.2) answers a count of values in a range without changes. With changes, a Fenwick tree of sorted vectors or a block structure like this one is used; for $n$ near $10^5$ the sorted blocks have the shortest code.

### Sums along every k-th position (Theorem 5.5.3)

<CodeSnippet unit="5.5/step-sums" />

**How it works.** The table `table[k]` for a step $k$ below the threshold is filled from the right: the sum along $p, p + k, p + 2k, \dots$ is `a[p]` plus the sum along $p + k, \dots$, and the entries past the end are 0 (the table has $n + k$ entries so that `p + k` is always inside). A question with a small step is one lookup. A question with a large step walks `p, p + k, ...` and makes at most $n / B$ jumps. The program takes $B = \lfloor \sqrt n \rfloor$. The sums are `long long`.

**Alternative formulation.** Offline, group the questions by their step $k$ and, for each different step, build the table once and throw it away, so that the memory is $O(n)$: for each distinct $k < B$ the work is $O(n)$ and for the others a walk. With a changing array the tables would need an update for each step.

### The nearest red vertex, with paintings (Theorem 5.5.5)

<CodeSnippet unit="5.5/nearest-red" />

**How it works.** `red` holds every painted vertex and `pending` the ones painted since the last rebuild. `paint` adds the vertex to both and, when `pending` has `B` entries, calls `rebuild`, which runs a breadth-first search that starts from all vertices of `red` at once ([topic 4.1](../../phase-4/4-1-graph-traversal/)) and leaves in `best[v]` the distance from `v` to the nearest red vertex; then `pending` is emptied. `ask` takes `best[v]` and the tree distance from `v` to each vertex of `pending` (the lowest common ancestor of [topic 4.7](../../phase-4/4-7-lca/) gives each distance in $O(\log n)$ steps) and returns the smallest. The program takes $B = \lfloor \sqrt q \rfloor$ and paints vertex 1 first. The distances fit an `int`.

**Alternative formulation.** Process the operations offline: sort the questions by time and use a divide and conquer over time, which needs no batch size but is longer. For a path or another shape where the distance is a difference of two numbers, a plain ordered set of the painted positions gives the nearest one in $O(\log n)$ steps.

## 7. Bug catalogue

Each bug below was made by changing one line of a template and running the random stress test against the brute force; the input shown is the smallest one found.

### Bug: a whole block is given the full block length

Template: set a range to one value.

```cpp
asg[b] = 1, val[b] = x, sum[b] = x * B;                 // instead of x * (hi(b) - lo(b) + 1)
```

Input: `5 2`, then `0 0 0 0 0`, then `1 1 5 4` and `2 1 5`.

Wrong output `24`, correct output `20`. With $B = 2$ the blocks are $0..1$, $2..3$ and $4..4$; the last block has one position, but the line gives it $2 \cdot 4 = 8$. The last block can be shorter than $B$ (Theorem 5.5.1, step 5), so its length must be computed.

**Fix:** use the length of the block, `hi(b) - lo(b) + 1`.

### Bug: a partial change on a block that holds a pending value

Template: set a range to one value.

```cpp
// in assign, the call  push(b);  before the single-position loop is missing
```

Input: `4 3`, then `1 1 1 1`, then `1 1 4 5`, `1 2 2 0` and `2 1 4`.

Wrong output `19`, correct output `15`. The first operation assigns 5 to the blocks $0..1$ and $2..3$ as wholes; `a[]` still holds the old 1s. The second operation changes position 2 alone: without the push, `sum[0] += x - a[i]` uses the stale `a[1] = 1` instead of the pending 5, and the sum of the block ends up at $10 - 1 = 9$ instead of $5$ (Theorem 5.5.1: the true value is not `a[i]` while a note is pending).

**Fix:** call `push(b)` before changing single positions of a block that the range only cuts through.

### Bug: the old value stays in the sorted copy

Template: count the values between two bounds.

```cpp
// the line  s.erase(lower_bound(s.begin(), s.end(), a[i]));  is missing at the start of set
```

Input: `1 3`, then `3`, then `1 1 8`, `1 1 5` and `2 1 1 3 7`.

Wrong output `2`, correct output `1`. After the two changes the array holds $5$, but the sorted copy holds $3, 5, 8$ (the old values were never removed), so the count between 3 and 7 finds two values. The copy must hold exactly the values of its block (Theorem 5.5.2, step 1).

**Fix:** erase one copy of the old value before inserting the new one.

### Bug: the walk for a large step starts one jump too late

Template: sums along every k-th position.

```cpp
for (p += k; p < n; p += k) s += a[p];                  // instead of for (; p < n; p += k)
```

Input: `1 1`, then `6`, then the question `1 2`.

Wrong output `0`, correct output `6`. The sum along $p, p + k, \dots$ includes $a_p$ itself. The wrong loop skips the first position, so a question with a large step and a start that is the only position in the range returns 0 (Theorem 5.5.3, step 1: the sum is $a_p$ plus the rest).

**Fix:** start the loop at `p` without the first jump.

### Bug: the question ignores the paintings since the last rebuild

Template: the nearest red vertex.

```cpp
int ask(int v) const { return best[v]; }                 // instead of also taking the minimum over pending
```

Input: `2 4`, then the edge `1 2`, then `2 2`, `2 1`, `2 2`, `2 1`.

Wrong output `1000000000`, `1000000000`, `1000000000`, `1000000000`, correct output `1`, `0`, `1`, `0`. With $q = 4$ the batch is $B = 2$ and the only painted vertex (vertex 1) is still in `pending`, so the table has no entry for it yet and every question reads the starting value (Theorem 5.5.5, step 3: the answer is the smaller of the table and the recent marks).

**Fix:** take the minimum of `best[v]` and the distance to every vertex of `pending`.

### Bug: the rebuild starts only from the new paintings

Template: the nearest red vertex.

```cpp
for (int v : pending) best[v] = 0, bfs.push(v);          // instead of for (int v : red)
```

Input: `3 4`, then the edges `1 2` and `2 3`, then `1 3`, `1 2`, `1 2`, `2 1`.

Wrong output `1`, correct output `0`. The second rebuild runs after the third painting; it starts the search only from vertex 2, the vertices painted since the first rebuild, and forgets vertex 1, which is red from the start. The table then says 1 for vertex 1 instead of 0 (Theorem 5.5.5, step 2: a rebuild must cover every mark made so far).

**Fix:** start the search from every red vertex, not only from the recent ones.

## 8. Worked examples

### Example 1: Little Elephant and Array

[Codeforces 220B: Little Elephant and Array](https://codeforces.com/problemset/problem/220/B). In short: an array of $n \le 10^5$ numbers and $m \le 10^5$ questions $(l, r)$; for each, print how many numbers $x$ occur exactly $x$ times among $a_l, \dots, a_r$.

#### Step 1: Constraints → budget

$n = m = 10^5$. Counting the values of each range is up to $10^{10}$ steps, about 100 seconds. About $\sqrt n \cdot (n + m) \approx 10^8$ steps is fine.

#### Step 2: Question form → candidate tools

- Count the values of each range ([topic 0.5](../../phase-0/0-5-brute-force/)): $O(nm)$.
- Prefix sums for every value ([topic 1.2](../../phase-1/1-2-prefix-sums/)): one table of $n$ entries for each of up to $n$ values is $n^2$ memory.
- A sorted order of the questions with a count array that moves along the array: possible, but it needs a bound on the work that this course does not give here.
- A threshold: the card "Split by a threshold of about $\sqrt n$".

#### Step 3: Property check → decision

A value $x$ can occur exactly $x$ times in a range only if it occurs at least $x$ times in the whole array. The sum of such values is at most $n$, so there are at most $\sqrt{2n} \approx 447$ of them. Decision: for each of these values, one pass over the array builds the prefix counts, and each question reads two of them.

#### Step 4: Proof for this problem

By Theorem 5.5.6, the set $H$ of values with at least $x$ occurrences has at most $\sqrt{2n}$ elements, and a value outside $H$ never occurs exactly $x$ times in a range. For $x \in H$ the prefix counts give the number of occurrences in $[l, r]$ as `prefix[r] - prefix[l - 1]` (1-based), and a question's answer is the number of $x \in H$ for which this equals $x$. One pass per value takes $O(n + m)$ steps, in all $O(\sqrt{n}(n + m))$.

### Example 2: Array Queries

[Codeforces 797E: Array Queries](https://codeforces.com/problemset/problem/797/E). In short: an array of $n \le 10^5$ numbers $a_p$ with $1 \le a_p \le n$ and $q \le 10^5$ questions $(p, k)$. Starting at $p$, repeat $p \to p + a_p + k$ until $p > n$; print the number of repetitions.

#### Step 1: Constraints → budget

$n = q = 10^5$. A question with $k = 1$ and all $a_p = 1$ makes about $n / 2$ jumps; $q$ such questions make $5 \cdot 10^9$ steps. A walk is at most $n / k$ jumps; a table for each step of size $n$ costs $n$ steps to fill.

#### Step 2: Question form → candidate tools

- Simulate each question ([topic 0.5](../../phase-0/0-5-brute-force/)): $O(nq)$ in the worst case.
- A table for every $k$: $n^2$ memory.
- A threshold on $k$: the card "Split by a threshold of about $\sqrt n$".

#### Step 3: Property check → decision

Every jump is at least $k + 1$ places, so for $k \ge B$ a question makes at most $n / B$ jumps. For $k < B$ the number of jumps from $p$ is $1 +$ the number from the next position, which depends only on $(p, k)$: a table of $n$ numbers for each small $k$, filled from the right. Decision: $B \approx \sqrt n \approx 316$.

#### Step 4: Proof for this problem

The jump from $p$ with step $k$ is $p \to p + a_p + k$, which depends only on $p$ and $k$. So the count from $p$ is $1 + \text{count}(p + a_p + k)$ when that position is inside the array, and 1 otherwise: this is the table recurrence of Theorem 5.5.5 with $a_p + k$ in place of the fixed step. Filling it from the right needs $n$ steps for each $k < B$, and a walk for $k \ge B$ makes at most $\lceil n / (B + 1) \rceil$ jumps.

### Example 3: GukiZ and GukiZiana

[Codeforces 551E: GukiZ and GukiZiana](https://codeforces.com/problemset/problem/551/E). In short: an array of $n \le 5 \cdot 10^5$ numbers and $q \le 5 \cdot 10^4$ operations. Either add $x$ to $a_l, \dots, a_r$, or, for a value $y$, print the largest $j - i$ with $a_i = a_j = y$ (or $-1$ if $y$ does not occur).

#### Step 1: Constraints → budget

$n = 5 \cdot 10^5$, $q = 5 \cdot 10^4$. Applying an addition to every position and scanning for $y$ is $n$ steps per operation, $2.5 \cdot 10^{10}$ in all. About $\sqrt n \approx 700$ steps per operation is $3.5 \cdot 10^7$, well within the limit. Values grow up to about $5 \cdot 10^{13}$: 64-bit.

#### Step 2: Question form → candidate tools

- Direct update and scan ([topic 0.5](../../phase-0/0-5-brute-force/)): $O(n)$ per operation.
- A Fenwick tree ([topic 5.2](../5-2-fenwick/)) or a segment tree ([topic 5.3](../5-3-segment-tree/)) with a tag: the addition composes as a tag, but "does a value $y$ occur in this node" is not a function of a small node; the node would have to keep all its values.
- Blocks with a sorted copy and a note: the card "Range operations with a note per block of about √n positions".

#### Step 3: Property check → decision

For a whole block the addition is one number (a note), and "does $y$ occur" becomes "does $y - \text{note}$ occur among the block's stored values", one binary search in the sorted copy. The ragged ends change a few positions, and then that block's sorted copy is rebuilt. Decision: blocks of about $\sqrt n$ positions.

#### Step 4: Proof for this problem

By Theorem 5.5.1, an addition costs at most two ragged ends of at most $B$ positions each and at most $n / B$ notes. Each ragged end also rebuilds one sorted copy, $O(B \log B)$. For a question, the first block (from the left) in which $y - \text{note}$ occurs holds the smallest position of $y$, and the first from the right holds the largest; a scan inside that block finds the position in $B$ steps. So an operation costs $O(n / B \cdot \log B + B \log B)$ steps, and $B \approx \sqrt n$ balances them.
